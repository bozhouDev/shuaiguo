# P7-6b · 对局图集瘦身：不让重构换来 4.4MB 包体和 64MB 显存

先读：`port/tmp/p7-6/report.md`（尤其"素材清单与成本"和"发现但未改"）、`cocos/tools/pack-match-atlas.py`、`cocos/assets/scripts/view/MatchNodes.ts`、`RetainedWorld.ts`、`match-atlas-data.ts`、`WorldAssets.ts`、`cocos/assets/resources/atlas/`、`AGENTS.md`（`assets/px` 体积预算、调色板 PNG 做法 `assets_pixel/build_px.py`）。

## Claude 验收 P7-6 的结论

- 重构本身达标，可以留：第 5 关 draw call 155→30，脚本耗时约减半，定格对比肉眼一致，黄金录像 100/100。
- **不能这样提交的问题**：新图集 `match.png` 是 4096×4096 RGBA。
  - 下载体积 4.4MB，原来全部图集加起来才约 2MB。
  - 显存 64MiB。
  - 原来按角色分的图集仍然被外围页面加载，两份同时驻留。
  - 手机内存吃紧会导致微信杀进程、发热，等于把性能问题换了个地方。iOS 微信小游戏内存上限比原生 App 低得多。

## 要做的

1. **下载体积**：`match.png` 改成调色板（索引色）PNG，做法同 `build_px.py`；像素素材本来就是有限色板，必须无损，逐像素校验解码结果和原 RGBA 一致。目标：新增下载 ≤ 1.5MB。
2. **显存**：
   - 文字缓存区不要占用精灵图集的下半张。拆成独立的、较小的动态纹理（按实际峰值定尺寸，比如 1024×1024 或 2048×512），写清楚满了怎么办。
   - 精灵部分按实际占用裁成最紧的尺寸（允许非 2 的幂；确认 WebGL1 / 微信下 NEAREST + 不生成 mipmap 时可以用，并在报告里引用引擎依据）。
   - 去重：外围页面（大厅、介绍、结算、排行等）用到的同一批角色 / 图标帧，改为也从对局图集取，原来的分角色图集能不加载就不加载。逐个列出每张旧图集还被谁用、能否停用。
   - 目标：全游戏同时驻留的贴图显存，比 P7-6 之前（只有分角色图集时）不增加，最好减少。用引擎真实纹理列表算出前后数字（宽 × 高 × 4 字节加总，按"大厅、对局中、结算"三个时刻分别统计）。
3. **包体**：给出构建后各分包体积的估算（主包、resources、audio），对照微信限制（主包 ≤ 4MB，总包 ≤ 30MB），确认没有超。

## 不能破坏的

- P7-6 的性能结果不能退：第 5 关 draw call 仍 ≤ 50，脚本耗时不升高。用 `perf-bench.mjs` 复测 10 秒、100 秒、119 秒。
- 画面和 P7-6 交付时完全一致：调色板是无损的，所以 1 / 3 / 5 关定格逐像素应该是 0 差。外围页面换图集来源后，大厅、介绍、结算也逐像素比对。
- 黄金录像（源码 + compiled）100/100，其余门槛全过。

## 不许做的

不运行 CocosCreator，不构建，不提交。不改原型，不改玩法，不降分辨率和帧率，不用有损纹理压缩。

## Claude 裁定（第一轮交付后，2026-11-04）

第一轮做到的：拆出文字纹理、裁掉空白、停用 12 张重复旧纹理，三个时刻显存都低于 P7-6 前。对局定格 0 差。这些全部保留。三项未过的，按下面裁定继续做：

1. **下载：用分片，不再单独发 match.png。**
   - 删掉 `match.png`，以及它的 meta、打包器里对应的输出。
   - 加载时直接用现有 12 张索引色角色 / misc PNG 当来源，按 `match-atlas-data.ts` 现有的帧位置拷进同一张 GPU 纹理，布局不变，好让对局继续 0 差。
   - 拷贝方式参考引擎 `dynamic-atlas-texture.ts` 的 `copyTexImagesToTexture`，或同等不改引擎的接口。
   - 来源只建 ImageAsset，不要为它们各自建一份常驻 Texture2D；拷完释放能释放的。
   - 写清楚：拷贝在微信小游戏下走哪条路径（引擎依据）、WebGL1 / 2 都要实测、加载峰值内存多少、首次进对局的耗时变化，并在源码验证页里实测。
   - 目标：相对 P7-6 之前，新增下载约等于 0。
2. **外围 0 差**：我看了大厅的热图，差异都是缩小绘制的精灵在纹素边界上的零散单像素。换了纹理尺寸以后，最近邻取样落到相邻纹素，不是画面变差。**我接受这类差异**，条件如下：
   - 每张图用连通块统计证明没有成片差异（单个连通块不超过 3 像素）。
   - 差异只出现在精灵内部的纹素行 / 列分界上，或精灵边缘。
   - 文字、颜色块、UI 底板没有差。
   - 换成分片方案后重新出大厅、介绍、结算的图，按这几条判。
3. **脚本耗时**：单轮 +2.6% 判不了。改成前后各交替跑 3 轮（前、后、前、后、前、后），报中位数和范围。中位数上升不超过 3%，或者落在两侧各自的波动范围以内，就算没有升高。

其余要求（显存不超过 P7-6 前、draw call ≤ 50、黄金 100/100、门槛全过、不跑 Creator / 不构建 / 不提交）不变。报告写到 `port/tmp/p7-6b/report.md` 末尾新增一节「第二轮」，implementation-notes 同步。

## Claude 验收（第二轮后，2026-11-04）

- 改正我自己的判据：裁定里"单个连通块 ≤ 3 像素"定错了。纹素行或列整条翻转时，画出来天然是一条 1 像素粗的线，看面积会误判。
- 改为看厚度：把所有超过 3 像素的差异块逐块算了粗细，大厅 / 介绍 / 结算 / 119 秒横幅**全部只有 1 像素粗**，都是单行或单列的最近邻翻转。
- 119 秒横幅的 80 像素块，是横幅上沿边框的一行，在两种边框深浅之间翻转。放大 3 倍并排看，分辨不出来。
- 结论：视觉条件按新判据通过，整卡验收通过，提交。
