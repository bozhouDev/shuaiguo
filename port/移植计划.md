## 1. 目标和"不能更差"的验收标准

**最终目标：** Cocos Creator 3.8.8（本机已装）做出微信小游戏版，接微信云开发；网页包作为附带产物。

"移植后只能更好，不能更差"不能只靠眼看，拆成五条能检查的标准：

| 维度 | 怎么算"没变差" | 怎么验 |
|---|---|---|
| 玩法逻辑 | 同一随机种子、同一关卡，新旧两版每一帧的状态完全一致（位置、锅、背锅、名次、事件） | **黄金录像对比**（见 §3.2），5 关 × 多个种子，全部一致才算过 |
| 数值平衡 | `simulate` 统计结果和原型一致 | 新旧两版各跑 5 关 × 200 局，过关率、名次分布、压垮数对齐 |
| 画面与界面 | 每个界面、每种提示、每个特效都在，位置和观感不比原型差 | **功能清单**逐项打勾 + 375×812 新旧截图并排对比 |
| 手感 | 摇杆、甩锅、反甩窗口不变；不掉帧 | 真机试玩 + 帧率记录（目标机型待定，见 §8） |
| 加载与体积 | 首次进入时间、包体不超标 | 主包 ≤ 4MB；首屏到大厅的时间，真机计时 |

**有意的改进**（变好）必须单独列出、单独提交，不能混在移植里。移植阶段的原则是"先一模一样，再改好"。

## 2. 现状盘点

| 项 | 现状 | 移植时要注意 |
|---|---|---|
| 代码 | 原生 JS 约 4400 行：`game.js` 3022、`engine.js` 1048、`levels.js` 314 | `game.js` 里逻辑和画面、DOM 混在一起（约 80 处 DOM 操作），要先拆开 |

| 测试 | `tests/` 下有 Node 跑真实逻辑的测试架子和周四、周五回归 | 要搬到新逻辑层上继续跑，这是防退化的主力 |

## 3. 关键技术决策（我的建议，待确认）

### 3.1 逻辑和画面彻底分开：三层结构

```
cocos/assets/scripts/
  core/      纯 TypeScript 玩法逻辑：关卡数据、对局状态、AI、计分、事件。不引用 cc，不碰画面、声音、存储
  view/      Cocos 画面层：读 core 的状态画出来，把输入交给 core；core 抛出的事件（播音效、飘字、震屏）在这里处理
  platform/  平台接口：存储、广告、分享、震动、云开发。微信一套实现，网页一套实现（网页版不接云，照现在只存本地）
```

理由：
- `core/` 能在 Node 里直接跑，黄金录像对比、批量模拟、回归测试都不用开 Cocos。
- 以后调平衡、做联机、做服务端校验，都基于同一份逻辑。
- 网页包和微信包只差 `platform/` 一层。

### 3.2 防退化的主手段：黄金录像

1. **先改原型**（P0，唯一允许动原型的地方）：把所有 `Math.random` 换成一个可设种子的随机数函数，模拟用固定步长。随机数的分布不变，对玩法没有影响。
2. 用现有 `tests/game-harness.cjs` 跑原型：5 关 × 若干种子，玩家交给 AI，每 0.5 秒记一份状态快照（所有人的位置、锅数、每口锅剩余时间、背锅数、领导状态、事件），存成"黄金录像"。
3. TS 版 `core/` 用同样的种子跑，快照必须**逐项一致**（浮点按小数点后 4 位比）。
4. 只要逻辑是忠实翻译、随机数调用顺序不变，就能做到完全一致。哪里不一致，就说明哪里翻译错了，能直接定位到第几秒、哪个人。

这一招是"不犯错"的核心：逻辑层的正确性不靠人眼，靠机器逐帧比对。

### 3.3 固定步长

> **2026-11-03 裁定：不做固定步长，改为和原型一致的可变步长（dt 上限 33ms）。** P2 证明 core 对任意 dt 都和原型逐帧一致，可变步长手感和原型完全相同，高刷手机也不抖；录像测试仍用固定 1/60。下面是原建议，留作记录。

对局逻辑改成固定步长（建议 1/60 秒），画面按帧插值。好处：手机帧率波动时手感一致、录像能复现。
风险：和原型"按真实帧间隔走"相比，手感有极细微差别。黄金录像用固定步长对比，手感靠真机试玩确认。

### 3.4 界面全部用代码搭，不依赖编辑器拖场景

Cocos 的场景和预制体是带 UUID 的大 JSON，AI 很难可靠地编辑，改了也很难审查。建议：
- 场景只有一个空 Canvas 和一个启动脚本，所有节点在 TS 里创建。
- 好处：Codex 能写、我能审、git 能看出改了什么。
- 代价：泊舟不能在编辑器里拖着调界面，调布局要改代码。

### 3.5 Cocos 工程放在仓库的 `cocos/` 子目录

和原型同一个仓库、同一个 `main` 分支。原型留在根目录，作为对照，直到 Cocos 版全部验收通过。

### 3.6 移植期间原型冻结玩法

移植开始后，原型不再加新玩法、不再调数值，否则两边都要改，黄金录像也会一直失效。
确实要改的，先在原型改并重录黄金录像，再同步到 TS，一次只做一件。

## 4. 分阶段计划

每个阶段有**验收门槛**，没过门槛不进下一阶段。阶段内的任务由我拆成任务卡交给 Codex。

### P0 · 基线和准备（Claude 主做，泊舟办账号）

- 原型改可设种子的随机数 + 固定步长模拟（唯一一次改原型），录 5 关黄金录像。
- 写**功能清单**：从原型里逐项列出每个界面、按钮、提示、群消息、特效、音效触发点、存档字段。这是 P3、P4 的验收表。
- 原型打标签 `prototype-final`，各界面截图存档。
- **门槛：** 黄金录像能稳定复现（同种子跑两次一致）；功能清单你过目确认。

### P1 · 工程骨架和构建链（Codex，先做一个小试验）

- 建 `cocos/` 工程，代码搭界面的启动方式，`core / view / platform` 三层目录。
- **先验证命令行构建能不能用**：Codex 不能点编辑器，必须确认 `CocosCreator --build` 能在命令行导入素材、出微信包；微信开发者工具命令行能预览、出二维码。这一步不通，整个协作方式要调整。
- 素材管线：图集转 Cocos 能用的格式，像素图关掉平滑（最近邻采样），字体转 TTF 子集，分包方案定下来。
- Node 里能跑 `core/` 的测试命令。
- **门槛：** 一个空场景显示一张像素角色，在开发者工具和你的手机上都能跑；主包体积报告。
- **P1 完成情况（2026-11-03）：** 泊舟安卓真机扫码通过（像素图清晰、字体正常、点击有声）。未裁剪的微信包 2.8MB，引擎约 2.6MB；裁剪设置已改，等下次编辑器构建对比。微信「分离引擎」按 Cocos 3.8 文档仍计入首包，不作为省主包的手段。
- **留给正式字体流程的待查项：** `body.ttf` 子集的字体名显示为 "Noto Sans SC Thin"，要确认实际字重是原型用的 700 / 900；编辑器浏览器预览里标题看起来没用上站酷快乐体（真机正常），正式接字体时两端都要核对。

### P2 · 逻辑核心移植（Codex 翻译，Claude 逐帧对比）

- 按顺序翻译：工具函数和随机数 → 关卡数据 → 地图寻路 → 锅和飞行 → 甩锅和反甩 → 领导 → 同事 AI → 事件和日程 → 画饼、小舅子、老板娘、发火、查岗 → 带教流程 → 结算和星级。
- 原型的周四、周五测试改写成 TS 版继续跑。
- `simulate` 移植，数值统计对齐。
- **门槛：** 5 关 × 至少 20 个种子黄金录像全部一致；回归测试全过；200 局统计对齐。
- **黄金录像没覆盖、P2 要另补测试的：** 带教流程（录像用 `makeState(false)`）、玩家手动输入（录像里玩家由 AI 托管）、表扬贴纸（定为画面层）、`finish` 结算计算（录像只跑到 `S.over`）。录像快照直接用原型的内部字段名，TS 版通过 `verify.cjs --adapter` 做字段映射。
- **P2-1 完成情况（2026-11-03）：** TS core 跑 100 组录像 100/100 一致；把 TS 的 `PARRY_WIN` 改 0.01、同事出手概率改 0.01，录像都能定位到具体关卡、种子、秒数。
- **P0 完成情况（2026-11-03）：** 100 组录像（5 关 × 种子 1001–1020，dt 1/60）连跑两次全部一致；把 `PARRY_WIN` 改 0.01 后录像能定位到具体关卡、种子、时间和字段。

### P3 · 对局画面（Codex，Claude 截图对比）

## 5. 云开发：要做的功能（2026-11-03 定：全部做）

前提：现在单机、数据存本地。云的作用是"加分"，任何云功能挂了，游戏都要照常能玩。

| 功能 | 价值 | 用什么做 | 我的建议 |
|---|---|---|---|
| **好友排行**（每关总账，比谁背锅少） | 戳"怕输、嫉妒"，和"甩给微信好友"的分享是一套，传播价值最高 | 这个**不靠云开发**，靠微信关系链（开放数据域 + `wx.setUserCloudStorage`），Cocos 要单独建一个开放数据域子工程 | 首发就做 |
| **远程调参** | 关卡数值放云数据库，调难度不用重新提审 | 云数据库 + 启动时拉取，拉不到用包内默认值 | 首发就做，成本低、收益大 |
| **云存档** | 换手机进度不丢 | 云函数取 openid + 云数据库 | 可以做，量不大 |
| **数据埋点** | 每关开局数、过关率、在哪一秒被压垮、广告看了多少 | 微信自带的 We 分析 + 云数据库存自定义事件 | 首发就做，没有数据没法调平衡 |
| 全服排行 | 和陌生人比 | 云数据库 + 云函数做合理性校验（逻辑全在前端算，只能防明显作弊） | 做 |
| 素材放云存储 | 音频等大文件不进包 | 云存储 / CDN | 看分包后体积再定 |

注意：
- 你现有的 Umami 统计、Dokploy 服务器在美国，小游戏请求的域名要求备案过的国内域名，**用不了**，所以埋点也要走云开发。
- 如果以后老板名要出现在分享卡片或上传到云端，用户自己输入的文字要过微信内容安全检查（`msgSecCheck`）。现在只存本地、只自己看，不需要。

## 6. 风险和坑（按严重程度）

1. **上线资质**（最长的周期，不在代码里）：
   - 主流说法：个人主体的纯广告小游戏，凭软著 + 游戏自审自查报告可以无版号上线，但不能做内购；企业主体通常要版号。各地执行尺度不一，要以微信官方和新闻出版署的最新规定为准。
   - 资质由泊舟自己办，开发侧不管（2026-11-03 定）。
   - 流量主（广告）要过审发布后、达到条件才能开通，复活、顶包这些广告功能上线初期可能用不了，要有不看广告的降级方案。
2. **命令行构建走不通**：Cocos 部分操作依赖编辑器，Codex 不能点界面。P1 第一件事就是验证，走不通就要你在编辑器里配合点几下，协作方式要改。
3. **主包超 4MB**：素材已经 4.5MB，必须分包；字体从 woff2 转 TTF 会变大，可能要把标题字换成位图字。
4. **右上角胶囊冲突**：现在 HUD 的设置、暂停按钮在右上角，正好被微信胶囊按钮挡住，要重新排。
5. **界面重做的观感**：CSS 的阴影、动画、排版，在 Cocos 里要重新实现，最容易出现"能用但不如原来好看"。靠功能清单 + 截图对比兜底。
6. **低端安卓性能**：代码画的扇形、地板每帧重画很费；人多的关（周四、周五 8 人 + 3 领导）最容易掉帧。要定一台测试机。
7. **emoji**：原型里还有少量 emoji（群消息里的奶茶、领导类型里的表情），不同手机显示不一样，DESIGN.md 也不让用，移植时顺手换掉（这属于"改好"，单独列出）。
8. **音频**：iOS 静音键、同时播放的音频数量上限、切后台回来 BGM 不响，都是小游戏常见问题。
9. **双份维护**：移植期间如果原型还在改玩法，两边会对不上（见 §3.6）。

## 7. 协作流程

```
泊舟定方向 → Claude 写任务卡 → Codex 执行 → Claude 审查（看代码 + 跑门槛） → 泊舟真机验收 → 提交
```

**任务卡模板**（我写给 Codex 的）：
- 目标：一句话
- 范围：改哪些文件，不许碰哪些
- 对照：原型里对应的函数和行号
- 验收：要跑的命令、要对比的录像或截图、功能清单的哪几项
- 不确定时：停下来报告，不自己改方向

**审查时我重点看：** 是不是忠实翻译（随机数调用顺序、判断条件、边界值）、有没有偷偷"顺手改好"、有没有漏掉功能清单里的项、中文注释是否齐全。

每个阶段结束在 `implementation-notes.md` 顶部记一节。
